## А. Имена событий в `ExtIdeHelpers.lua` — заглушки ⚠️ критично

Это стоило половины отладки и обязано попасть в документацию порта.

`ExtIdeHelpers.lua` (сгенерированный самой игрой) объявляет входные события как
`Ext.Events.EclLuaKeyInput`, `EclLuaMouseButton`, `EclLuaControllerButton`. **Все они
существуют как объекты, `Subscribe` на них не бросает исключение — и возвращает `nil`.
Подписка молча не создаётся, обработчик не вызывается никогда.**

Рабочие имена в v32 — **без префикса `EclLua`**:

| Из IDE-хелперов (не работает) | Рантайм (работает) | id подписки |
|---|---|---|
| `EclLuaKeyInput` | **`KeyInput`** | 68719476737 |
| `EclLuaMouseButton` | **`MouseButtonInput`** | 73014444033 |
| `EclLuaControllerButton` | **`ControllerButtonInput`** | 85899345921 |
| `EclLuaViewportResized` | **`ViewportResized`** | 90194313217 |
| `EclLuaMouseWheel` | `MouseWheel` — тоже `nil` | — |

`Tick`, `GameStateChanged`, `SessionLoaded` работают под своими именами.
`pairs(Ext.Events)` возвращает пустоту — таблица проксирована, перечислить имена нельзя,
только пробовать по одному.

> **Нормативно для порта**: после каждой подписки проверять, что `Subscribe` вернул не `nil`.
> Молчащий обработчик здесь — штатное поведение, а не ошибка.

## E1 — подавление клавиш ✅

После перехода на `Ext.Events.KeyInput` события пошли сразу. Восемь физических нажатий
(`J`, `J`, `Ctrl+K`) дали корректный поток:

```
J      down  mods=SDLKeyModifier()        canPrevent=true
J      up    mods=SDLKeyModifier()        canPrevent=true
LCTRL  down  mods=SDLKeyModifier(LCtrl)   canPrevent=true
K      down  mods=SDLKeyModifier(LCtrl)   canPrevent=true
```

**`CanPreventAction == true` на каждом событии**, модификаторы отражаются правильно.

Дальше — A/B/A на клавише `J` (журнал заданий) в загруженной сессии:

| Фаза | `PreventAction()` | Результат на экране |
|---|---|---|
| A | выкл | журнал **открылся** |
| B | вкл (2 попадания в хук, `ActionPrevented=true`) | журнал **не открылся** |
| A′ | выкл | журнал **открылся** |

**§8.2 спеки закрывается штатно: подавление per-chord работает.** Стратегия переноса
биндингов остаётся как запасная, но не обязательна.

Отдельный факт: **`Ext.ClientInput.InjectKeyPress` не поднимает `KeyInput`.** Инъекция идёт
ниже уровня Lua-хука. Для слоя это плюс — собственные инъекции не возвращаются в свой же

## E4 — дерево Noesis читается полностью ✅

`Ext.ClientUI.GetRoot()` даёт корень, обход идёт по **двум** деревьям (`VisualChild(i)` +
`Child(i)`, индексы **1-базовые**), и весь текст на экране доступен.

Снимок главного меню (401 узел, глубина 22) вернул ровно то, что видно на экране:

```
Продолжить · Новая игра · Загрузить игру · Сетевая игра · Менеджер модов ·
Параметры · Авторы · Выход из игры · Учетная запись Larian · Войти
Текущая игра: Брок · Область: Наутилоид в аду · Сложность: Путешественник ·
Дата: 18/6/2024 23:14
```

Сверено со скриншотом — совпадение полное. Локализация подхватывается сама.

**Два открытия по способу чтения:**

1. **`ToString()` возвращает `Класс: содержимое`.** Кнопка «Продолжить» —
   `ls.LSButton: Продолжить`, текстовый узел — просто `Продолжить`. Тип Larian и метка
   достаются одним вызовом. `Ext.Types.GetObjectType()` отдаёт лишь привязанный базовый
   класс Noesis (`Noesis::FrameworkElement`) и для рецептов бесполезен.

2. **Текст берётся из `GetAllProperties()`**, поля `Text` и `DataContext`. Полный дамп узла
   даёт ~28 свойств: `FontSize`, `Foreground`, `IsVisible`, `Style`, `TemplatedParent`,
   `PlayerId`. Для §A6 (parity) есть `IsVisible`, для ролей — префикс `ls.LS*`.

Иерархия типов Larian видна прямо в пути:

```
ls.UICanvas / Viewbox / Decorator / Grid / ls.UIWidget: Grid / Border /
ContentPresenter / Grid / Control / StackPanel / Grid /
ls.LSButton: Продолжить / ls.LSNineSliceImage: ContentPresenter / ... / ContentPresenter
```

**Ограничение**: в загруженной игре тот же обход отдал имена спутников («Лаэзель», «Брок»),
цель задания («Рулевая рубка») и координаты, но **не отдал текст активного диалога**. Либо
обход упёрся в потолок узлов (обход без дедупликации визуального и логического деревьев
раздувается), либо диалоговый слой висит на отдельном Noesis-view вне обойдённого корня.
Это первый вопрос, который надо закрыть при написании рецепта диалога.

## E5 — стоимость обхода ✅ (и главная ловушка производительности)

Четыре режима, 5 прогонов каждый:

| Режим | мкс/узел | Найдено строк |
|---|---|---|
| только структура (дети) | **1.91** | — |
| структура + `ToString()` | **2.38** | 19 897 |
| структура + `GetAllProperties()` | **7.15** | 3 172 |
| структура + `GetProperty("Text")`/`("Name")` | **290.8** | 0 |

**`GetProperty` на отсутствующем имени бросает исключение и пишет строку в лог движка** —
в **150 раз** дороже. Первый прогон дал 4 мс на узел и залил лог тысячами
`Noesis::ObjectHelpers::GetNamedProperty(): Object Grid has no property named 'Text'`.

> **Нормативно для порта**: никогда не вызывать `GetProperty` по угаданному имени.
> Только `GetAllProperties()` один раз на узел, дальше чтение из таблицы.

При 7.15 мкс/узел полное чтение экрана в 2000 узлов — **14 мс**. Для иммедиат-режима §A2
это приемлемо на операцию, но не покадрово для всего дерева: рецепт должен читать своё
поддерево, а не корень.

## E3 — `ICommand` в BG3 нет ❌ ← ОШИБКА, СМ. §С1

> **Отменено 30.07.2026.** Этот вывод неверен. `GetAllProperties()` на `ls.LSButton`
> отдаёт `Command = Noesis::ICommand`, а также `CommandBindings` и `InputBindings`;
> `CanExecute()` возвращает `true`, а `Execute()` реально активирует пункт меню. Обход,
> на котором строился E3, до этих свойств не добирался. Подробности и границы
> применимости — в §С1. Текст ниже сохранён как есть, чтобы видна была история ошибки.

Из 401 узла главного меню **ни один не имеет свойства `Command`**, `CommandBindings` пуст.
Larian не использует WPF-паттерн команд — `ls.LSButton` работает через собственные
обработчики и `ls.LSInputBinding` (такие узлы в дереве присутствуют).

**Последствие для P2**: путь «дёрнуть обработчик UI напрямую» закрыт. Остаются два:
инъекция клавиш (для интерфейса) и Osiris (для мира). §8.3 из спеки перестаёт быть
опасностью и становится **основным** механизмом воздействия на интерфейс.

## E8 — диалоги 🟡

`Ext.Utils.GetDialogManager()` доступен **на сервере**. В активном диалоге с Лаэзель, где на
экране было три варианта ответа, менеджер вернул ровно три записи:

```json
{ "id": 94, "state": 5, "speakers": 6, "localHighlighted": -1,
  "resource": "c62d7e26-beb5-0afe-becd-68a25c7f4314",
  "answers": [ {"uuid":"cf574f36-..."}, {"uuid":"8ba4192d-..."}, {"uuid":"d45d24db-..."} ] }

На экране в этот момент:
```
1. Кто ты и почему ты мне помогаешь?
2. Трудно удержаться от вопросов. Зачем нам в рубку?
3. Уйти.
```

**Структура подтверждена**: количество, порядок и идентичность узлов совпадают.

Это задача на полчаса, но требует активного диалога под рукой.

## E6 — файловый мост ✅

`Ext.IO.SaveFile` пишет в `%LOCALAPPDATA%\Larian Studios\Baldur's Gate 3\Script Extender\`,
`Ext.IO.LoadFile` читает оттуда же — **контекст по умолчанию и `"user"` работают,
`"data"` возвращает nil**. Мост двусторонний.

**Стоимость записи** (200 итераций, строка ~25 байт):

| min | медиана | p95 | max | среднее |
|---|---|---|---|---|
| 0.29 мс | **0.49 мс** | 5.98 мс | 6.47 мс | 2.64 мс |

**Round-trip игра → компаньон → игра** (30 циклов, компаньон опрашивает файл каждую 1 мс):
ровно **33.2–33.5 мс**, разброс менее 0.4 мс. Это не файловая система, а период игрового
тика: `Ext.Timer.WaitForRealtime(4, ...)` реально срабатывает раз в кадр.

**Вывод**: для речи значима только запись — **0.5 мс медиана**, полностью приемлемо.
Ограничение в 33 мс касается обратного канала, который речевому слою не нужен.
**Вариант A из отчёта подтверждён.**

## Б. Мод не грузится через `modsettings.lsx` ⚠️

Диагностический мод собран корректно (`Divine.exe -a create-package`, содержимое pak
проверено), положен в `%LOCALAPPDATA%\...\Mods\`, запись добавлена в `modsettings.lsx`.
**Игра при старте переписала файл, выбросив запись**, дважды подряд.
`Ext.Mod.GetLoadOrder()` показывает только 13 базовых модулей.

Причина — встроенный менеджер модов Patch 8: он ведёт собственный список и затирает ручные
правки. Пути для реального мода:

1. включение через внутриигровой менеджер модов;
2. BG3 Mod Manager с экспортом порядка загрузки;
3. на время разработки — **подача кода прямо в консоль SE**, что и использовалось здесь и
   что оказалось быстрее: правка файла + одна команда, без пересборки pak.

## С1. `ICommand` существует — E3 отменён

`GetAllProperties()` на `ls.LSButton` (кнопка «Продолжить», 36 свойств):

```

CommandParameter = <есть у части кнопок>   InputBindings   = Noesis::BaseCollection
Name             = ContinueButton          SoundID         = UI_HUD_MainMenu_Continue
BoundEvent       = <UICancel / UIAccept / UIDelete у части кнопок>

```

`CanExecute()`, `CanExecute(nil)`, `CanExecute(DataContext)` — все три возвращают `true`.
`Execute()` **реально открывает экран**: после вызова на «Загрузить игру» дерево выросло
с 469 до 833 узлов, кнопок с 13 до 23.

**Граница применимости, и она жёсткая.** Активация работает только у пунктов **без**
`CommandParameter`:

| Пункт | `Name` | `CommandParameter` | `Execute` |
|---|---|---|---|
| Продолжить | `ContinueButton` | — | ✅ |
| Новая игра | `NewGameButton` | — | ✅ |
| Загрузить игру | `LoadGameButton` | — | ✅ |
| Сетевая игра | `MultiplayerButton` | — | ✅ |
| Выход из игры | `QuitGameButton` | — | ✅ |
| Менеджер модов | `ModsButton` | `OpenModBrowser` | ❌ |
| Параметры | `OptionsButton` | `OpenOptions` | ❌ |
| Авторы | `CreditsButton` | `OpenCredits` | ❌ |
| Учётная запись | `LarianAccountBtn` | `OpenSignUp` | ❌ |

Причина отказа: `Execute` требует живой C++ объект, а параметр приходит строкой.
`GetAllProperties()` схлопывает его в `"OpenOptions"`, и `GetProperty("CommandParameter")`
**тоже отдаёт строку** — живой объект через биндинг недостижим:

```
Param 2: expected a light C++ object, got string
```

Коварно то, что `Execute(DataContext)` при этом возвращает `ok=true` и **не делает
ничего**. Именно так «Отменить» и «Параметры» сначала выглядели доказательством того,
что команды вообще инертны.

> **Нормативно**: `Command` — механизм принципиально частичный. Проверять наличие
> `CommandParameter` и не считать `ok=true` признаком того, что действие произошло.
> Проверка — по смене состояния экрана, а не по коду возврата.

Полезный побочный результат: **`Name` даёт стабильный идентификатор** там, где метка
локализована, а **`BoundEvent` задаёт роль** кнопки (`UICancel` — назад, `UIAccept` — ок).

## С3. Фокус в клавиатурном режиме есть, но его нечем двигать 🟡

Вопреки исходному предположению, Noesis **держит настоящий клавиатурный фокус** и в
мышином режиме: полная цепочка `IsKeyboardFocusWithin` от `ls.UICanvas` вниз и
`IsFocused` + `IsKeyboardFocused` на первой кнопке. Появляется он в момент активации
окна игры и исчезает, когда фокус окна уходит.

Сдвинуть его не удалось **ничем** из проверенного:

| Способ | Результат |
|---|---|
| `node:Focus()` | ❌ методов у узлов нет вообще: `Property does not exist: Noesis::FrameworkElement::Focus` |
| Обход табом (Tab / Shift+Tab) | ❌ фокус не двигается |
| Стрелки, WASD | ❌ не двигается (подтверждено и вживую) |
| Инъекция `UIUp`/`UIDown` в очередь движка | ❌ очередь съедается, фокус на месте |
| `Ext.ClientUI.SetState` | ❌ `Deprecated`, `GetStateMachine()` → `nil` |

Проверено, что **ни один метод Noesis не привязан**: из 11 опробованных
(`Focus`, `BringIntoView`, `GetVisualOffset`, `CaptureMouse`, …) все дают «свойства не
существует». Биндинг отдаёт только свойства.

## С4. Геймпадный режим — рабочий фундамент ✅

Гипотеза выдвинута пользователем и подтвердилась целиком. С настоящим геймпадом:

- фокус **ходит** по пунктам и **читается** из дерева как `IsFocused`;
- активация идёт **родным обработчиком игры**, поэтому работают и те четыре пункта,
  которые через `Command` недостижимы — «Параметры» открылись;
- подсветка и звуки фокуса/подтверждения достаются бесплатно.

Следилка (`M.watchStart`) на `Ext.Events.Tick` с частотой ~10 Гц озвучивала пункты
главного меню по мере перемещения — это одновременно и проверка, и прототип.

**Ограничение**: игра переключает интерфейс обратно в мышиный режим на **любом** вводе с
клавиатуры, включая Alt+Tab. Из-за этого любое наблюдение «снаружи» показывало KBM-версию,
а не то, что было на экране у тестировщика, — часть выводов сессии из-за этого
пришлось переделывать. Диагностика должна срабатывать **изнутри игры**.

Найден флаг для сосуществования: `ControllerAllowKeyboardMouseInput` — записывается
(`false` → `true`). Его влияние на переключение режима до конца не проверено.

## С5. Очередь инъекций движка ✅

`Ext.ClientInput.GetInputManager()` отдаёт 17 полей, среди них:

```
DeviceEventInjects = Array<input::InjectDeviceEvent>   -- {DeviceId: uint16, EventId: uint32}
InputInjects       = Array<input::InjectInputData>     -- непрозрачный, членов нет
Events             = Array<input::FireEventDesc>       -- {DeviceId, Event, EventDesc, InputId, PlayerIndex}
AllowDeviceEvents  = false                             -- ГЕЙТ
ControllerAllowKeyboardMouseInput = false              -- записывается
PerDeviceData      = Array<input::InputDevice>         -- 12 устройств: id 0, 1, 3, остальные 65535
```

Дозапись `a[#a+1] = {DeviceId=…, EventId=…}` проходит. **Но при `AllowDeviceEvents = false`
запись лежит в очереди вечно**; после `= true` очередь опустела за 2 секунды, то есть
движок её вычитывает. Это объясняет, почему первые инъекции не давали ничего вообще.

Идентификаторы навигации (из реестра 323 событий, E11):

```
UIUp=245  UIDown=246  UILeft=243  UIRight=244
UIAccept=223  UICancel=225  UIEnter=83  UIHome=89  UIEnd=90
```

Фокус эти инъекции не двигают. Вероятная причина: `InjectDeviceEvent` — событие уровня
**устройства**, а не ввода; у него нет значения, тогда как у `input::InputEvent` есть
`NewValue`/`OldValue` типа `input::InputValue {State, Value, Value2}`. Путь через
`Events`/`FireEventDesc` не пробован.

**Инъекция клавиш работает** и доходит до игры: `InjectKeyPress("ESCAPE", 0)` поднял
`UICancel` и закрыл панель. Сигнатура — `(SDLScanCode, SDLKeyModifier)`, метки принимаются
строкой. Есть также `InjectKeyDown` и `InjectKeyUp` отдельно (не пробованы).

> **Вывод**: стрелки не навигируют не потому, что инъекция не проходит, а потому что у
> клавиатуры **нет привязки** к `UIUp`/`UIDown`. Таблица привязок читается
> (`InputScheme.InputBindings`, у первого игрока 308 привязанных событий), но поля
> отдельной привязки через `pairs` не читаются — правка привязок не пробована.

## С6. Подэкраны через дерево недостижимы ❌

`Ext.ClientUI.GetRoot()` **не следует за активным экраном**. Пока открыты «Параметры» или
загрузка, он отдаёт либо `nil`, либо всё то же дерево главного меню — 442 узла и те же
42 строки («Текущая игра», «Брок», «Сложность»…). Все «снимки подэкранов» оказались
снимками главного меню; это была моя ошибка интерпретации, замеченная пользователем.

Проверено тремя независимыми способами:

1. содержимое экрана параметров не появилось в дереве **ни разу**;
2. корень уходит в `nil` (`focus lost (0 nodes)`) и возвращается уже с главным меню;
3. подъём вверх по `Parent`: всего два уровня, `ls.UICanvas` → `AdornerDecorator`, выше
   родителя нет; обход сверху даёт 479 узлов против 477 от корня — **соседних view нет**.

`GetRoot(i)` игнорирует аргумент. Вся поверхность `Ext.ClientUI` — девять функций
(`EnableErrorReporting`, `GetCursorControl`, `GetDragDrop`, `GetPickingHelper`, `GetRoot`,
`GetStateMachine`, `Instantiate`, `RegisterType`, `SetState`), перечисления view среди них
нет.

**Не все экраны такие.** Сетевая игра в дереве появилась: 1514 узлов, 163 строки, с
геймпадным текстом про разделённый экран. То есть Larian смешивает: часть экранов —
виджеты внутри общего канваса, часть — отдельные поверхности. Это та же природа, что у
недочитанного текста диалогов в E4.

**Мышь как обход не подтверждена.** `IsMouseOver` отражает реальный курсор ОС (запись
`WindowCursorPos` из E2 управляет прицелом мира, а не попаданием в интерфейс — три разные
позиции дали одну и ту же кнопку). Инъекции мыши в API нет вовсе. Сканирование столбца
меню настоящим курсором из компаньона показало пустое наведение во всех точках, включая ту,

**Настройки**: `Ext.Utils.GetGlobalSwitches()` → тип `GlobalSwitches`, **148 полей**

## Нормативные правила инструментария

Каждое стоило ошибочного вывода, поэтому они здесь, а не в комментариях к коду.

1. **Узлы Noesis живут меньше тика.** Сохранённая ссылка мертва на следующем кадре
   (`got Noesis::FrameworkElement whose lifetime has expired`). Хранить стабильный
   идентификатор (`Name`, иначе метку) и заново находить узел в том же тике, где он нужен.
2. **Внутри обработчика `KeyInput` чтение свойств урезано.** `ToString()` метку отдаёт, а
   `GetAllProperties()` возвращается без `Command`, `BoundEvent` и `IsEnabled`. В
   обработчике — только `PreventAction()` и постановка действия в очередь; вся работа с
   интерфейсом на `Tick`.
3. **Консоль SE принимает только ASCII.** Кириллица приезжает знаками `?` и роняет чанк
   (`unfinished string near <eof>`). Русский текст живёт в `.lua` (читается как UTF-8 через
   `Ext.IO.LoadFile`), через консоль передаются ASCII-ключи. В `console-send.ps1`
   поставлена защита.
4. **Консоль стартует в серверном контексте**, а строка, отправленная до её готовности,
   теряется. На главном меню сервера нет, поэтому клиентские вызовы падают с
   `Cannot queue server commands in game state Uninitialized`. Посылать `client` и
   убеждаться в приглашении `C >>`.
5. **Перезагрузка модуля не снимает подписки.** `load()` создаёт новую таблицу, а старое
   замыкание продолжает обрабатывать ввод. Идентификаторы держать в `_G.A11Y_*`,
   `A11y.dropAll()` перед `watchStart()`. Проверять, что счётчик тиков растёт **у текущего**
   экземпляра — иначе правка кажется неработающей, хотя просто не запущена.
6. **Никогда не спрашивать свойство по угаданному имени** — промах бросает исключение,
   пишет в лог движка и стоит ~150× попадания (E5). Это касается и `IsFocused`: обход
   доходит до невизуальных объектов (`Boxed<String>`, `ls.VMInputEvent`), у которых его нет.
   Один `GetAllProperties()` на узел, дальше чтение таблицы; обход делать прерываемым.
7. **Незафокусированная игра не обрабатывает ввод и молчит.** Курсор, инъекции и звук
   уходят в пустоту, а `MuteSoundWhenNotFocused = True` глушит аудио. Перед тем как верить
   отрицательному результату — проверять активное окно (`tools/focus-window.ps1`).

## Архитектура, к которой пришли

Три уровня, каждый подтверждён на живой игре:

1. **Где view достижим** — читать фокус игры и озвучивать. Навигация остаётся за игрой.
2. **Где недостижим** (параметры, загрузка) — экран не читать вообще, а строить свой
   линейный список из модели данных. Модель доступна независимо от открытого экрана.
3. **Действия** — отдавать геймпаду: он активирует всё родными обработчиками, включая
   параметризованные команды.

Виртуальный пад (ViGEm-класса, в компаньоне) нужен только чтобы это водилось с клавиатуры —
и это единственная внешняя зависимость, которую придётся объяснять пользователю мода.

## D1. `ui::UIWidget` — механизм экранов, и почему ECS не помог

`Ext.Types.GetTypeInfo` знает всю машинерию интерфейса:

```
ui::UIStateMachine   PlayerID, RootState, State:ui::UIStateInstance, States
ui::UIStateInstance  Widgets:Array<ui::UIWidget>, StateWidgets:Array<Noesis::UIElement>,
                     State:ui::UIState, States:Array<Array<ui::UIStateInstance>>
ui::UIWidget         WidgetContainerGrid:Noesis::FrameworkElement, XAMLPath:STDString,
                     WidgetData:ui::UIStateWidget, StateGuid:Guid
ui::UIStateWidget    Filename, Layer, SoundLayer, Libraries, IgnoreHitTest
```

То есть у каждого экрана есть свой корень (`WidgetContainerGrid`) и имя файла (`XAMLPath`).
**Получить сам объект не удалось**: `Ext.ClientUI.GetStateMachine()` возвращает nil и с
аргументом 0, 1 и 2 (D2).

Клиентский ECS отдаёт **3234 сущности**, среди компонентов ровно то, что нужно:

```
gui::registration::VMGlobalDataSingletonComponent   gui::input::TrackingSingletonComponent
gui::registration::VMCharacterDataSingletonComponent  gui::UIReadyComponent
ecl::sound::UIPanelStateSingletonComponent         ecl::ui::PadCursorVisibleComponent
```

`GetRegisteredComponentTypes()` их перечисляет, `HasRawComponent(имя)` отвечает `true` —
но **SE их не биндит**: `GetComponent` бракует имя (`not a valid 'ExtComponentType' enum
label`), `GetAllComponents()` для этих сущностей пуст, а в `Ext.Enums.ExtComponentType`
(1067 меток) ни одной `gui::` нет.

> **Нормативно**: путь через ECS к интерфейсу в SE v32 закрыт. Компонент видно, данных нет.

## D4. Что такое экран

Сравнение структурных срезов дерева с открытым подэкраном и без него:

```
ls.UICanvas CanvasRoot
  Viewbox ViewboxRoot
    Decorator
      Grid ContentRoot
        ls.UIWidget MainMenu             vis=True  → при открытии загрузки vis=False
        ls.UIWidget LoadGame             vis=True  sub=342  «Загрузка»
        ls.UIWidget ModDownloadingWidget vis=True  sub=15   «0»

        ls.UIWidget CrossplayOverlay     vis=True  sub=6

**Экран = `ls.UIWidget` под `ContentRoot`.** Имя узла — идентификатор экрана, `IsVisible` —
открыт ли он, порядок — z-order.

Отсюда объяснение, почему слой молчал на подэкранах, и оно не имеет отношения к
достижимости: **`MainMenu` остаётся в дереве под модалкой со своим собственным `IsFocused`**,

Слой читал нижний слой стопки и озвучивал то, чего на экране нет.

> **Нормативно**: никогда не читать от `GetRoot()`. Сначала выбрать активный `ls.UIWidget`,
> дальше работать только внутри него.

**Правило выбора активного** (без списка имён оверлеев, который пришлось бы вести вручную):
сверху вниз по z-order; выигрывает виджет со сфокусированным элементом, иначе — первый, у
кого есть содержание. «Содержание» это ≥2 строк и ≥20 узлов: `ModDownloadingWidget` висит
над меню всегда и содержит один символ-счётчик «0», чего хватало, чтобы он побеждал главное
меню по правилу «первый с текстом».

При бюджете кадра 16 мс. Причины, в порядке вклада:

1. два полных обхода дерева на тик (читалка + запись таймлайна) на 10 Гц;

## D9. `ControllerMode = 2` — клавиатура водит геймпадный интерфейс ⭐

Найдено пользователем вживую: в параметрах есть настройка схемы управления
(**Авто / Клавиатура / Контроллер**), и если выставить «Контроллер», то

1. клавиатурный ввод **перестаёт** сбрасывать интерфейс обратно в мышиный режим — уходит
   ограничение §С4, из-за которого любое наблюдение снаружи показывало не тот UI;
2. геймпадные действия **дублируются на клавиатуру**: стрелки двигают меню, Enter активирует.

Это поле `GlobalSwitches`:

```
ControllerMode = 0   (было в сессии 2, «Авто»)
ControllerMode = 2   (после переключения на «Контроллер»)
```

**Но выставить его из мода нельзя** — это выяснилось следующим же шагом и опровергает
поспешный вывод, сделанный по §С7 (там писалось *булево* поле):

```
gs.ControllerMode = 0
-> Cannot set property GlobalSwitches::ControllerMode - property is read-only
gs.ShowTextBackground = true   -> ok (для сравнения, тут же)
```

Обход через интерфейс тоже не сработал. У строки «Режим ввода» находится `ls.LSComboBox` со
списком `Авто | Клавиатура | Контроллер`, и `node:SetProperty("SelectedIndex", …)`,
`SetProperty("SelectedItem", …)`, `item:SetProperty("IsSelected", true)` — **все три
возвращают `ok` и меняют виджет, но не настройку**: `SelectedIndex` уехал с 2 на 0, а
`ControllerMode` остался 2. Привязка не срабатывает от прямой записи свойства зависимости.

> **Нормативно** (третий случай подряд, после `Execute` в §С1 и `DeviceEventInjects` в §С5):
> в этом движке успешный возврат ничего не значит. Проверка только по смене состояния.

**Практическое следствие**: режим переживает только физическое присутствие пада. При
отключении геймпада игра сбрасывается в «Авто», при обратном подключении не восстанавливается,
и вернуть его можно лишь походом в экран параметров. Это делает виртуальный пад снова
осмысленным — не ради навигации, которая теперь не нужна, а ради того, чтобы устройство
никогда не «отключалось».

**Инъекция клавиш теперь двигает фокус.** Проверено из консоли при неактивном окне игры:

```
before:        MainMenu_c -> Продолжить
after DOWN:    MainMenu_c -> Новая игра  …  -> Параметры -> Авторы -> Выход из игры
after RETURN:  открылся Options_c (1087 узлов)
```

Сравнить с §С3, где не сработало **ничто**: `Focus()`, обход табом, стрелки, инъекция
`UIUp`/`UIDown` в очередь устройства, `SetState`.

> **Следствие для плана**: виртуальный пад больше не нужен **для навигации** — клавиатура
> водит интерфейс сама. Но он остаётся нужен для **устойчивости режима**, см. ниже: снять
> зависимость от физического устройства иначе пока нечем.

Побочно это ускоряет саму разработку: экраны теперь открываются и обходятся из консоли, без
участия тестировщика.

1. **Текст варианта лежит на глубине 28–29** (Run внутри `ls.LSSpan` внутри `ls.LSWrapPanel`

## D13. Навигация по миру ⭐

Без перемещения остальные механики непроверяемы, и это оказался первый случай, где нужны
**оба контекста сразу**: видит клиент, ходит сервер.

**Клиент знает всё о мире.** Ключ — метка `ClientControl`, которой помечена ровно одна
сущность: управляемый персонаж. Не надо искать, кто из партии активен.

```
ClientControl                    1 сущность  — тот, кем играют
ClientCharacter                  64          — все существа уровня
PartyMember                      2
Transform.Transform.Translate    позиция     (-42.57, 8.09, -356.36)
Transform.Transform.RotationQuat поворот
Steering.TargetRotation          куда поворачивается (не куда смотрит)
GetEntitiesAroundPosition(p, 20) 17 объектов
```

Позиция с клиента совпала с `Osi.GetPosition` на сервере до сантиметра.

**Сканер** (`Nav.scan`) даёт список ближайших объектов с именем, типом, направлением по
циферблату и дистанцией, за **0.5 мс**:

```
1. Мертвый раб, существо, на час, 2 м
2. Лаэзель, спутник, прямо, 2 м
3. Артериальная сетка, налево, 2 м
8. Сфинктер, дверь, налево, 15 м
```

Радиус переспрашивается: движок отдаёт по ячейкам сетки, а не по расстоянию (E7), поэтому
дистанция считается заново и лишнее отбрасывается.

**Движение — на сервере.** Доступны `CharacterMoveTo`, `CharacterMoveToPosition`,
`TeleportToPosition`. Проверено живьём: персонаж пошёл и дошёл, с поиском пути и анимацией.
К объекту предпочтительнее, чем к координате: движок останавливается на дистанции
взаимодействия, а не пытается встать внутрь предмета.

**Мост между половинами — штатный канал расширителя**, а не файл: `Ext.Net` есть с обеих
сторон (`PostMessageToServer` / `RegisterNetListener`, `Ext.Events.NetMessage`). Файловый
мост остаётся для речи, где обратный канал не нужен.

```
[client] going to #5: Мертвая рабыня, существо, 11 м
[server] move to object 44779e34-… ok=true
before (-41.25, -356.71)  →  after (-43.74, -365.19)
```

**Не выверено**: порядок компонент в кватернионе не документирован, поэтому направление
(«прямо», «на час») может оказаться зеркальным или повёрнутым. Обе трактовки считаются в
`Nav.calibrate`, выбирать надо по живой проверке — молча ошибающийся указатель хуже, чем
никакого.

## D14. Бой ⭐

Бой не проверялся ни в одной сессии — и оказалось, что новых механизмов он не требует, всё
лежит на клиенте.

```
Health            Hp, MaxHp, TemporaryHp, IsInvulnerable
CombatParticipant CombatHandle (задан = в этом бою), InitiativeRoll, Flags(CanFight)
TurnBased         IsActiveCombatTurn — чей ход, CombatTeam — кто с кем, RequestedEndTurn
```

**`CombatHandle` — это сама сущность боя.** У неё `CombatState.Participants` (18 сущностей),
`CombatState.Initiatives` и компонент `TurnOrder` с группами и порядком. Спрашивать её
напрямую и правильнее, и дешевле, чем обходить уровень — **и приходится**, потому что
`GetAllEntitiesWithComponent("CombatParticipant")` на клиенте возвращает **ноль**, хотя тот
же компонент прекрасно читается у каждой сущности по отдельности. (`TurnBased` при этом
отдаёт 190, а `CombatState` — одну.)

**В составе боя половина — декорации.** «Резервуар наутилоида», «Пустотный клубень»,
«Объект» числятся участниками с инициативой −20 и без флага `CanFight`. Из 16 «врагов»
настоящих оказалось 5, и без этого фильтра сводка хоронила их под мусором.

Итог, 0.57 мс:

> Ход: Лаэзель. Вы 15 из 23. Врагов 5. Мелкий адский кабан, 5 из 5, на одиннадцать, 5 м.
> Младший бес, 4 из 4, на семь, 6 м. Иллитид, 43 из 59, на четыре, 11 м.
> Командир Жалк, 105 из 105, на четыре, 13 м.

### Перебор целей — механизм самой игры

Замечено пользователем: крестовина влево/вправо в бою перещёлкивает цели, и этот список
правдивее любого, что собирает сканер, — в нём ровно то, по чему можно действовать, и в том
порядке, в каком игра его обходит. Живёт он в помощнике прицеливания:

```
GetPickingHelper(1).Selection.field_0_Entity      что под прицелом
GetPickingHelper(1).Selection.field_8_TurnOrder   его номер в цикле, с нуля
GetPickingHelper(1).SelectableObjects             весь цикл (7 целей)
```

Озвучка перебора стоит 116 мкс и потому проверяется каждый проход читалки, а не раз в
полсекунды: игрок жмёт влево-вправо именно затем, чтобы услышать следующую цель.

> Младший бес, 4 из 4, на семь, 6 м, 4 из 7

**Чего нет**: самой атаки. Выбор умения идёт через панель быстрого доступа, которая не
разобрана. Ближайшее к ней — `ActionResources_c` («Действие, Бонусное действие, Движение
30,0»), то есть остаток действий на ходу.

## D15. Задача боя, и как найти то, что в ней названо ⭐

Не всякий бой выигрывается убийством. Этот — «Доберитесь до передатчика до того, как
наутилоид разобьется!», на часах пятнадцать ходов, и **ничего из этого не произносилось**,
хотя оно определяет всё поведение игрока.

И задача, и часы лежат в виджете `Minimap`, рядом с координатами и маркером обновления,
которые надо отбросить:

```
X:-52 Y:-391
[ForceUpdate]
Доберитесь до передатчика до того, как наутилоид разобьется!
Осталось ходов: 12
```

**Как найти названный в задаче объект.** Слова задачи режутся на основы **без первой буквы**,
и получившийся байтовый префикс ищется среди имён объектов:

```
задача → стемы: оберите | ередатч | азобьет
совпало: Передатчик, на восемь, 30 м
```

Отсечение первой буквы решает сразу две задачи: падеж («до передатчика» против
«Передатчик») и регистр — `string.lower()` в Lua кириллицу не трогает, а сравнивать
как-то надо.

**Радиус тут принципиален**: передатчик в 30 метрах, а прицел игры перебирает только то, до
чего можно дотянуться. Поэтому широкий обзор (60 м, 92 объекта, 2.4 мс) — не роскошь, а
единственный способ вообще узнать, куда идти.

## D16. Гибрид: пад ведёт игру, клавиатура ведёт слой ⭐

Предложено пользователем и оказалось лучшим решением проблемы, которая копилась всю сессию:
**на паде в бою нет свободных кнопок**. Крестовина перебирает цели, лицевые кнопки — игры,
клики стиков уже заняты сближением и сводкой. Каждая новая команда приходилось куда-то
впихивать — отсюда и двойное нажатие R3, и смена смысла L3 в бою.

Клавиатура снимает это целиком, и именно `ControllerMode = 2` сделал её безопасной: набор
больше не перекидывает интерфейс в мышиный режим (D9). События идут через
`Ext.Events.KeyInput` независимо от того, какой интерфейс на экране, `PreventAction()` на них
подтверждён ещё в E1.

```
Page Up / Page Down   предыдущий / следующий объект
Home / End            пересканировать и первый / последний
Insert                сводка: окружение, в бою — бой с таймером
Delete                идти к выбранному
Pause                 где я
```

Работает без режимов: не надо входить в обзор и не надо отбирать крестовину у игры.

> **Нормативно**: клавиатурные привязки **нельзя проверить инъекцией** —
> `InjectKeyPress` не поднимает `KeyInput` (E1). Только физическое нажатие.

**Отдельная ловушка инструментария, стоившая цикла отладки**: правка `.lua` через PowerShell
`Set-Content -Encoding UTF8` дописывает BOM, `load()` на нём возвращает nil, `Var = load(…)()`
падает — **и в памяти остаётся прежний модуль**. Пуш рапортует успех, а новых функций нет.
Снимать `tail -c +4`, а лучше не править эти файлы через оболочку.

## Что это меняет в архитектуре

Трёхуровневая схема из сессии 2 («где view достижим — читать, где недостижим — строить свой
экран из модели») **упрощается до одного уровня**: view достижим всегда, читать надо активный
`ls.UIWidget`. Модель данных (`GlobalSwitches`, `ExistingSaves`) остаётся полезной как
источник значений и структуры, но перестаёт быть обязательным обходным путём.

Виртуальный пад из планов сессии 2 меняет назначение. Для **навигации** он не нужен — при
`ControllerMode = 2` игра сама принимает клавиатуру в геймпадном интерфейсе (D9). Но режим
держится только физическим присутствием пада: при отключении устройства игра сама сбрасывает
его в «Авто», выставить обратно из мода нельзя (поле только на чтение, запись в контрол игра
игнорирует), а инъекция в сброшенном режиме фокус не двигает. То есть виртуальный пад нужен
не чтобы ходить, а чтобы устройство никогда не «отключалось». Решено отложить: у игрока
геймпад есть.

**Управление сложилось гибридным** (D16): игру ведёт пад, слой — клавиатура. Это не компромисс
на время, а то, что следует из ограничений: свободных кнопок на паде в бою нет, а клавиш
десятки, и `ControllerMode = 2` сделал их безопасными.

**В сессии читается всё, что нужно для игры**: диалог с вариантами (D12), окружение с
дистанциями и направлениями (D13), бой с ходами и здоровьем (D14), задача боя с таймером
(D15). Не читается пока действие — то, чем бить.

## Что осталось после сессии 3

**Не проверено на слух** (написано по дампам, живьём не выверено):

1. **Направления** («прямо», «на час») — порядок компонент в кватернионе не документирован,

   Инструмент готов: `Nav.calibrate`.
2. **Клавиатурные команды** — подписка живая, но проверить можно только физическим нажатием
   (инъекция `KeyInput` не поднимает). Имена клавиш SDL могут отличаться (`PAGEUP` против
   `PRIOR`); незнакомые пишутся в лог как `key seen: ИМЯ`.
3. **Запас движения в пошаговом режиме** — уважает ли `CharacterMoveTo` остаток движения или
   идёт целиком.

**Не сделано:**

4. **Атака** — слой читает бой, но не бьёт. Вход — панель действий и `ActionResources_c`
   («Действие, Бонусное действие, Движение 30,0»), то есть сперва остаток действий на ходу,

5. **Взаимодействие** — открыть дверь, поднять предмет, обыскать тело. Навигация к объекту

6. **Инвентарь, журнал, лист персонажа** — виджеты в дереве есть, на линейную модель не
   переведены.
7. **Экран загрузки** (`LoadGame_c`) — фокус садится на `ls.LSToggleButton/ExpanderButton`

8. **Переключение вкладок с клавиатуры** — бамперы делают это на паде, `Q`, `E`, `Tab`,

9. **Режим обзора** собирает строки со всех вкладок сразу: скрытые вкладки помечены не через

10. **Оверлеи** (`Notification_c`, `ModDownloadingWidget`) иногда выигрывают выбор активного
    экрана на переходах.
11. **Заголовок экрана** берётся как первая строка виджета — не везде это заголовок.
12. **Мод как мод**: сейчас всё подаётся в консоль вручную, и загрузка сохранения обнуляет
    состояние клиента. Нужен загрузчик (§Б: `modsettings.lsx` переписывается менеджером

## E1. Режим ввода ставится без человека ⭐

§D9 оставил дыру: слой работает только при `ControllerMode = 2`, поставить его может только
человек в параметрах, а отключение пада сбрасывает настройку. Дыра закрыта — целиком снаружи:

1. **Прицел без глаз.** Noesis отдаёт `IsMouseOver` на каждом элементе, значит «подвинуть
   настоящий курсор и спросить дерево, кто под ним» — замкнутый цикл, которому не нужно
   зрение. `tools/hover-sweep.ps1` водит курсор по сетке, `Ms.mark` записывает попадания в
   JSON. Так снялась вся раскладка главного меню (x=300: Продолжить 480–500, Новая игра
   540–560, … Параметры 760–780) и строка «Режим ввода» в параметрах (x 600–1000, y 425–470).
2. **Геометрии в Noesis нет** — `ActualWidth` на узле с подписью равен 0, `Parent` есть, но
   абсолютных координат не отдаёт никто. Мерить перебором оказалось единственным путём.
3. **Выпадающий список комбобокса живёт вне виджета экрана.** `IsDropDownOpen` становится
   `true`, но обход `GameOptions` его не видит: это Noesis Popup в отдельном визуальном
   корне. Пункты находятся только обходом от `Ext.ClientUI.GetRoot()` — единственный случай,
   когда читать от корня правильно, потому что `IsMouseOver` пространственный и врать не
   может.
4. **Клик по пункту меняет `SelectedIndex`, но не настройку.** Значение применяется при
   выходе с экрана — и применил его **настоящий Escape**, а не что-либо из Lua.

Результат: `ControllerMode 0 → 2` без единого касания пада.

> Порядок: клик (300,770) → клик (975,447) по `ToggleButton#ComboBoxButton` → клик (800,560)
> по пункту `Контроллер` → `keys.ps1 -Key ESCAPE`.

## E2. Настоящая клавиатура водит геймпадный интерфейс ⭐

`Ext.ClientInput.InjectKeyPress` до Noesis не доходит — проверено ещё раз на открытом
комбобоксе: две инъекции `DOWN` не сдвинули `SelectedIndex` ни на единицу. Зато `SendInput`
со **скан-кодами** (`tools/keys.ps1`) — это ввод, неотличимый от пользовательского:
фокус ходит, экраны открываются, Escape закрывает. `tools/drive.ps1` соединяет всё в один
шаг: поднять окно, нажать, подождать, показать что сказал слой.

**Инъекция событий устройства по-прежнему мертва.** `AllowDeviceEvents = true`,
`DeviceEventInjects` принимает `{DeviceId=1, EventId=246}`, очередь растёт — фокус стоит.
§С5 подтверждён и в геймпадном режиме.

## E3. Почему стрелки работают не везде — таблица привязок ⭐

Читается через `im.InputScheme.InputBindings[1]`. Для player 1:

```
UIUp    245  dev3 dpad_up        | dev6400 tab +Alt,Gui        field_9=0
UIDown  246  dev3 dpad_down      | dev6400 tab +Gui            field_9=0
UILeft  243  dev3 dpad_left      | dev6400 tab +Ctrl,Alt,Shift
UIRight 244  dev3 dpad_right     | dev6400 tab +Ctrl,Shift
UITabPrev 267 dev3 leftshoulder  | dev6400 enter
UITabNext 268 dev3 rightshoulder | dev6400 enter
UIAccept  223 dev3 controller_a  | dev6400 enter
```

Клавиатурные строки (`DeviceId=6400`) — **заглушки**: `Win+Tab`, `Ctrl+Shift+Tab` и
`field_9=0` против 25 у пада. То есть навигация интерфейса привязана только к паду, а
стрелки работают там, где их обрабатывает сам Noesis (главное меню, колонка настроек
создания персонажа, лобби), и не работают там, где ходит игра: список сохранений внутри
группы, вкладки-шаги создания персонажа. Это не дефект слоя и чинится только перепривязкой.

## E4. LoadGame_c фокус держит — слой его не спрашивал ✅

Пункт 7 «что осталось» снят. Виджет `LoadGame_c` не отдаёт `FocusedElement`, но его потомок
`ls.LSToggleButton #ExpanderButton` честно рапортует `IsFocused` и `IsKeyboardFocused`.
Дешёвый путь §D6 возвращал nil, экран считался «без фокуса» и читался целиком — отсюда и
вывод «подсветка там не Noesis-фокус», который **неверен**.

Добавлен спуск по `IsKeyboardFocusWithin` как запасной путь, и `pathTo(root, target)` —
поиск предков *известного* узла. Спуск по флагу для этого не годится: на создании персонажа
`IsKeyboardFocusWithin` стоит вдоль всей панели, спуск уходит в соседнюю настройку и подпись
приезжает со сдвигом на строку («По выбору, Тип тела» вместо «Тип тела, 1»).

Группы сохранений теперь читаются как **«Лаэзель, группа сохранений, свёрнуто, 3 из 3»**:
имя берётся у потомка с `Name = "Title"` (собственный ToString у Expander — «Expander:
ListBox»), состояние из `IsExpanded`, позиция — счётом соседей. Раскрытие группы (`Enter`)
озвучивается сменой состояния.

## E5. Четыре бага чтения, каждый молча удалял содержимое ⭐

Их стоит держать вместе: все четыре выглядели как «экран не читается», а на деле текст был
на месте.

1. **`ipairs({ p.Text, label })` останавливается на первом nil.** У большинства узлов нет
   `Text`, значит `label` — где обычно и лежит подпись — не смотрелся никогда. Заменено на
   `A.strings(...)` / `A.firstText(...)`, которые пропускают дырки.
2. **Рамка nine-slice съедает бюджет обхода.** `Control #Frame` держит
   `ls.LSNineSliceImage` из ~30 `Image` плюс Column/RowDefinitions, и у спиннера создания
   персонажа рамка идёт **раньше** презентера со значением. Любой разумный лимит узлов
   тратится на картинки, и значение не достигается — поэтому каждая настройка читалась как
   одна подпись без значения. Добавлен список `NO_TEXT` (Image, Rectangle, Ellipse, Line,
   Path, Shape, Column/RowDefinition, LSNineSliceImage), в который не спускаются.
3. **Шаблонные заглушки.** Значение спиннера — узел, чей ToString равен `[ForceUpdate]`, а
   текст лежит уровнем ниже. Без фильтра каждый пункт читался как «[ForceUpdate], <значение>».
   Отсекается по форме `[...]`.
4. **Дедупликация по строке удаляла характеристики.** Блок способностей — колонка чисел, и
   вторая «10» на экране принадлежит другой характеристике. Из-за дедупликации по тексту
   «Интеллект» читался вообще без значения. Дедупликация по узлу не спасает: визуальное и
   логическое дерево дают **разные Lua-userdata на один элемент**, `tostring()` у них разный.
   Работает правило «схлопывать только соседние повторы»: дубли приходят подряд, а два
   одинаковых значения разделены названием характеристики.

## E7. Нормативные правила, добавленные к §9

- **Игра без фокуса окна не догружает уровень.** Переход в создание персонажа встал в
  `PrepareRunning` и висел там, пока окно было позади; вышло на передний план — доехало за
  секунды. К старому «без фокуса нет ввода и звука» добавляется загрузка.
- **`MainWindowHandle` у процесса игры может указывать на консоль Script Extender.** Она
  принадлежит тому же процессу, и стоит ей раз побывать впереди — Windows начинает считать
  главной её. Поднимать окно надо по заголовку (`focus-game.ps1` перебирает окна процесса и
  ищет то, что начинается на «Baldur»).
- **Консоль SE непригодна как канал обратной связи на больших экранах.** `GetAllProperties`
  логирует по строке на каждое непонятное свойство (`ls.LSButton:TapTime`,
  `ContentPresenter:DataContext of type 'ls.LocaString'`), и на экране в 900 узлов вывод
  вытесняется быстрее, чем читается. Работающие каналы — JSON-файлы и **лог речи**
  (`tools/speech-log.ps1` пишет каждую реплику в UTF-8 файл).
- **`LogRuntime: false`** в `ScriptExtenderSettings.json`: те же предупреждения писались ещё
  и на диск. С включённым логом и запущенным читателем игра встала намертво на экране
  параметров.
- **Тяжёлые пробы и читатель не должны работать одновременно.** Перебор курсором делает
  полный обход экрана на каждую точку; вместе с читателем это уронило игру. `Pad.stop()`
  перед перебором.
- **`Ms.flush` очищает накопленное.** Второй вызов после перебора перезаписывает результат
  пустым файлом — ровно так один перебор был потерян.

## E8. Режим ввода не переживает перезапуск — и это теперь чинится одной командой ⭐

Проверено прямо: поставили `ControllerMode = 2`, перезапустили игру — снова `0`. Настройка
**не сохраняется вообще**; в `graphicSettings.lsx` и `profile8.lsf` её нет, а `config.lsf`
сжат. Это и есть «у нас опять слетел режим ввода»: не пад отвалился, а игра стартовала.

Отсюда `tools/set-input-mode.ps1` — весь путь §E1 одной командой, с проверкой каждого шага:

```
tools\set-input-mode.ps1          поставить Контроллер
tools\set-input-mode.ps1 -Check   только сказать, какой сейчас
```

Проверяется всё: открылся ли экран параметров, раскрылся ли список, и — главное — **что под
курсором действительно пункт «Контроллер»** (сравнение делает Lua: в консоль русскую строку
не передать). Не сошлось — скрипт останавливается и говорит, что перемерить, вместо того
чтобы кликать вслепую по чужой настройке. Первый клик после запуска игры регулярно съедается,
пока меню доезжает, поэтому он повторяется до трёх раз.

**Запускать после каждого старта игры, до всего остального.**

## E9. В геймпадном режиме мыши нет вообще

Перебор курсором по экрану загрузки в режиме `ControllerMode = 2` дал **ноль попаданий** во
всех 35 точках: `IsMouseOver` не ставится нигде. «Только контроллер» означает буквально это —
hit-тест мышью выключен. Значит вся оснастка §E1 работает **только в мышином режиме**, что и
требуется: она нужна ровно для того, чтобы из него выйти. Обратная сторона — попасть мышью в
список сохранений или во вкладки создания персонажа нельзя: там нужен пад.

## E10. В сессии слой читает мир, но экраны надо было заткнуть

Загруженное сохранение, полный слой (`A11y`, `NavSrv`, `Nav`, `Pad`):

- `Nav.scan()` — 67 объектов вокруг;
- обзор списка: **«Резервуар наутилоида, на пять, 1 м, 1 из 67»**, «Мертвый раб, существо,
  на пять, 3 м, 5 из 67», «Младший бес, существо, налево, 5 м, 8 из 67» — имя, род,
  направление по часам, расстояние, позиция;
- быстрое сохранение по F5 проходит (`Брок-…__QuickSave_0` появляется на диске).

Но в сессии **фокуса нет ни на чём** (§D12), и читатель принимал каждый изменившийся виджет
HUD за новый экран: одно F5 давало «Лаэзель, 4 строк» и «Осмотреть, 3 строк», а ходьба —
то же самое без остановки. Теперь в сессии экран называется только если на нём есть что
читать (≥ 8 строк): инвентарь, журнал и лист персонажа проходят, значки HUD — нет. Вне
сессии правило не действует, меню объявляются любой длины.

**Имена клавиш надо узнавать у рантайма.** `Delete` приходит как `DEL`, а не `DELETE`, то
есть команда «активировать» не срабатывала ни разу с самого её появления. Способ проверки —
нажать и посмотреть `Pad.unknownKeys`; незнакомая клавиша попадает туда, знакомая нет.

## F1. Игра не видит мод, положенный снаружи ⚠️

Проверено в трёх видах, каждый раз с чистого запуска:

1. `BG3Access.pak` в `%LOCALAPPDATA%\...\Mods\` + запись в `modsettings.lsx` в формате Patch 8
   (атрибуты байт в байт как у `GustavX`: `UUID` типа `guid`, `PublishHandle`, без BOM);
2. то же, но модуль распакован в `<игра>\Data\Mods\BG3Access\`;
3. поиск мода во внутриигровом менеджере модов — там его нет вовсе (проверено человеком).

Во всех случаях `Ext.Mod.GetModManager().AvailableMods` — **16 базовых модулей и ни одного
нашего**, а запись из `modsettings.lsx` игра стирает при старте. То есть §Б был диагностирован
неверно: дело не в том, что менеджер «переписывает файл поверх», а в том, что **модуля для
игры не существует** — она чистит запись, под которую не нашла модуль.

`AvailableMods` — не таблица, а `Array<Module>`: `ipairs` по нему молча ничего не даёт, нужен

## F3. Прививка — установка, которая работает ⭐

Script Extender'у не нужен *мод*, ему нужна *папка*: он читает
`Mods/<Папка>/ScriptExtender/Config.json` у каждого модуля из порядка загрузки, причём через
файловую систему игры, а та накладывает россыпь файлов из `Data\` поверх паков. Значит, слой
можно положить в папку модуля, который загружен всегда:

```
<игра>\Data\Mods\GustavX\ScriptExtender\Config.json
<игра>\Data\Mods\GustavX\ScriptExtender\Lua\BootstrapClient.lua
<игра>\Data\Mods\GustavX\ScriptExtender\Lua\BootstrapServer.lua
<игра>\Data\Mods\GustavX\ScriptExtender\Lua\A11y\*.lua
```

Ничего не перезаписывается: подпапки `ScriptExtender` внутри `GustavX.pak` нет, это новые пути
в слитом дереве. Проверено до перезапуска — `Ext.IO.LoadFile(path, "data")` читает такие файлы
сразу после их появления, то есть монтирование россыпи динамическое.

В консоли на старте видно, что SE подхватил конфиг:

```
    'GustavX': SE v30; flags: Lua
Loading bootstrap script: Mods/GustavX/ScriptExtender/Lua/BootstrapClient.lua
```

Установка и снятие — `tools\graft-mod.ps1` (`-Uninstall` убирает всё без следа).

## F4. Три особенности Lua внутри мода, каждая молча ломает загрузку ⭐

- **`load` у SE — не Lua'шный**: второй аргумент это *таблица окружения*, а не имя чанка.
  Вызов `load(src, "@name", "t", env)` падает с `bad argument #2 to 'load' (table expected,
  got string)`.
- **`Ext.Require` живёт только пока SE выполняет файл загрузчика.** Отложенный в обработчик
  `Tick`, он падает с `Ext.Require() called without a mod, but the current mod UUID is not
  known!`. Поэтому модули грузятся на верхнем уровне файла, а стартует слой тиком позже —
  UI-корня и менеджера ввода на момент загрузки ещё нет.
- **Глобалы мода — это `Mods.<ModTable>`, а не консольные глобалы.** Проверено:
  `Pad=false, A11yBoot=false, Mods.BG3Access=true`. Модули передают друг друга через `_G`,
  внутри мода это его собственная таблица — поэтому `Ms = load(...)()`, набранное в консоли,
  собирает вторую, полуживую копию, которая не видит `A11y` и `Pad`. Всё в консоли теперь
  через префикс `Mods.BG3Access.`, а `A11yBoot.loadDev(имя, глобал)` кладёт dev-модуль туда,
  где живёт остальной слой.

## F5. «Авто» достаточно — принуждение к геймпадному режиму снято ⭐

Замерено живьём: `ControllerMode` остаётся **0**, а `_c`-экраны при этом подняты, слой читает
`MainMenu_c` и `Options_c` («Показывать обучение, Вкл., флажок, 1 из 33»). То есть при
настройке по умолчанию игра сама переключается на геймпадный интерфейс, как только берут пад,
и §D9 надо читать так: `ControllerMode = 2` нужен **не слою, а вождению игры с клавиатуры без
пада** (`tools\set-input-mode.ps1` остаётся ровно для этого).

Слой теперь следит не за настройкой, а за тем, есть ли на экране видимый виджет с суффиксом
`_c`, и говорит об этом один раз на изменение. С задержкой: `_c` мигают на обычных переходах
меню, и мгновенное объявление превращалось в «выключен / включен» подряд — потеря засчитывается
после трёх проверок, возврат сразу. Удержание `ControllerAllowKeyboardMouseInput` осталось: без
него любое нажатие клавиши (в том числе Alt+Tab) рушит геймпадный интерфейс, а команды слоя
живут как раз на клавиатуре.

## F7. В бою два прицела, и озвучивать надо оба ⭐

Игрок сообщил, что при переборе целей крестовиной слышит «Иллитид», но не слышит того, что
слой сказал про «Кровь иллитида». Это не сбой — это **два разных прицела**:

| Прицел | Чем двигается | Что им делают | Где читается |
|---|---|---|---|
| перебор целей | крестовина влево/вправо | бить, целиться заклинанием | `GetPickingHelper(1).Selection` (§D14) |
| мировой курсор | камера/левый стик | кнопка A: перейти, обыскать, использовать | **`CursorText_c`** |

`CursorText_c` — самая содержательная находка сессии: игра сама пишет там глагол, объект,
дистанцию и **причину отказа**. Пойманное в бою: «Перейти / Кровь иллитида / 104 фут /
Недостаточно движения» — четыре факта, три из которых никакой сканер собрать не может, потому
что это суждение игры о ходе, а не то, что стоит в мире.

Читается при изменении, но сравнение пришлось делать не по строке: виджет **подмигивает
составом** — стоя перед одним объектом он дал «Перейти, Кровь, 1,8 фут», потом «Кровь, 1,8
фут», потом «Перейти, Кровь», и одно и то же было сказано семь раз подряд. Поэтому ключ
сравнения строится без дистанции (она тикает непрерывно при ходьбе, а в фразе всё равно
звучит), и чтение, чьи слова — подмножество предыдущего, считается тем же самым. Плюс фильтр
мусора: сырые хендлы, `ResStr_*`, одиночные `~` и `*`.

## F8. Мировой курсор из Lua не наводится ❌

Обе кандидатуры в `ecl::PlayerPickingHelper` **принимают запись и держат её** — и ни одна не
двигает прицел:

- `WindowCursorPos` стоит ровно `{960, 540}` (центр экрана 1920×1080 — в геймпадном режиме
  курсор прибит к середине). Записан `{600, 400}`, удерживался 60 тиков: поле изменилось,
  `Inner.Position` не сдвинулся ни разу (`260.69 0.34 206.43`).
- `PickingDirection` записан вектором на реальный объект в 4 м, удерживался 60 тиков: поле
  изменилось, `Inner.Position` остался `0 0 0`, `CursorText_c` пуст.

Значит, это зеркала состояния, а луч строится выше по течению — от камеры. Полезное, что
попутно вскрылось: `Inner` — это **результат трассировки**: `Position`, `WorldPosition`,
`PlaceablePosition`, нормали, `AiGridTile`. То есть *куда* смотрит курсор, прочитать можно;
*задать* — нет.

Остаётся то, что и так работает: слой доводит персонажа до объекта (`Osi.CharacterMoveTo` по
объекту — движок сам останавливается на дистанции взаимодействия), а игра предлагает действие
и называет его в `CursorText_c`. Так и был применён передатчик: «Использовать» → «Рассказчик.
*Это передатчик рубки. Ты успела вовремя.*». Непроверенная идея на будущее — запись в
`Selection.field_0_Entity`, то есть подстановка цели в **игровой** перебор; в момент опыта боя
не было и `Selection` был пуст.

## F9. Навигатор по задаче на одной кнопке ⭐

R3 дважды подряд = «веди к задаче», и это один цикл без переключателей: перечитать задачу с
миникарты, найти названный в ней объект (сопоставление по огрызкам слов, §D15), и —

- дальше 2 м: отправить персонажа и сказать «иду: Передатчик, 3 м, на четыре»;
- ближе: «Вы на месте, действие — кнопка A»;
- объект не найден: текст задачи и «цель не видна поблизости».

Ничего не кэшируется между нажатиями: сканирование на 60 м стоит 2.4 мс, а устаревшая цель
хуже медленной — она уверенно ведёт туда, где ответ был раньше. Текст задачи повторяется
только когда изменился: на пятом нажатии подряд нужна дистанция, а не предложение.

Смена задачи объявляется сама (`questTick`, раз в полсекунды): выполнение одной задачи и
появление следующей — единственное событие в квесте, которое слепой игрок не замечает вовсе,
и это же момент, когда кнопка начинает вести в другое место.

Порог «вы на месте» намеренно короткий (2 м): движок сам останавливает ход на дистанции
взаимодействия, поэтому щедрый порог означал бы «вы на месте» там, где игра ещё отказывает.

## F10. Куда идти: метки карты живут в тексте миникарты ⭐

Игрока выбросило на берег, и вопрос «куда двигаться, чтобы шёл сюжет» оказался без ответа:
сканер честно перечисляет тростник, бочки и трупы, а что из этого продвигает игру — не
говорит. Искали маркер задачи, нашли следующее:

- **координаты на миникарте — это позиция игрока**, а не маркер: `X:258 Y:195` против
  `myPos 257.95 0.15 195.57`. Как цель не годится;
- в реестре 1640 компонентов есть `eoc::item::MapMarkerStyleComponent`,
  `ecl::markers::AvailablePortalComponent`, `eoc::party::WaypointsComponent` — но
  `GetAllEntitiesWithComponent("MapMarkerStyle")` возвращает **0** (та же ловушка, что с
  `CombatParticipant`, §D14), остальные имена не принимаются вовсе, а поштучный опрос всех
  сущностей в 60 м не нашёл ни одной с `MapMarkerStyle`;
- **зато подписи меток лежат прямо в тексте виджета `Minimap`**:

```
Заросшие руины
Древняя дверь
X:285 Y:290
МЕСТО КРУШЕНИЯ
```

Это и есть искомое: точки, к которым ведёт сюжет, названные словами. Разбор виджета теперь
делит его содержимое по признакам, а не по одной длине: строка с `Y:` — координаты, строка
вида `...: 12` — счётчик ходов, **прописными** — название местности, длинная фраза со
строчными — задача, короткая фраза со строчными — **подпись метки**. До этого «МЕСТО
КРУШЕНИЯ» проходило по длине как задача, и категория «задача» ловила всё, названное в честь
крушения (`questKeys = "РУШЕНИЯ"`).

Навигатор (§F9) теперь падает на метки: нет объекта задачи — ведёт к ближайшей метке
(«метка. Древняя дверь, 16 м, на семь»); нет и её — называет метки вслух, потому что даже имя
без направления говорит, куда смотреть.

## F11. Категории сканера

Список «всего вокруг» — не список: на берегу это 31 объект, из которых важен один. Категории:

## F12. «Какой кнопкой это открыть» — игра знает, надо просто спросить ⭐

стиков, а это `ToggleInputMode` и **`ShowWorldTooltips`** — подсветка всех интерактивных
объектов вокруг с их именами. Плюс режим обзора отбирал крестовину, то есть `PrevObject` /
`NextObject` и панель отдыха. Слой глушил ровно те кнопки, которые сам же и пытается заменить.

Поэтому: **`M.BUTTONS` пуст**, режима обзора больше нет (он существовал только чтобы одолжить
крестовину), а всё управление слоем — на клавиатуре, где свободных клавиш десятки. Эти клавиши
работают и в режиме «Контроллер», где игровые клавиатурные привязки мертвы (§F12), потому что
слой сидит на сыром событии Script Extender'а, а не на привязке игры.

| Клавиша | Действие |
|---|---|
| `PageUp` / `PageDown` | предыдущий / следующий объект |
| **`Alt`** + `PageUp` / `PageDown` | предыдущая / следующая категория |
| `Home` | идти к выбранному |
| `End` | навигатор: задача, её объект, а нет задачи — ближайшая метка |
| `Delete` | подойти к тому, что выбрано игровым перебором целей |
| `Insert` | то, что уместно сейчас: в бою — сводка боя, на экране — экран целиком, в мире — повтор последней фразы |
| `Pause` | где я: фокус и экран |

Навигатор переехал с `Insert` на `End`, а «какая категория открыта и сколько в ней» убрано
вовсе: это уже говорит само переключение категорий, и вторая кнопка для того же — лишняя.
`Insert` вместо этого делает то, что уместно в данный момент, а в открытом мире — повторяет
последнее сказанное, потому что именно за этим тянется рука, когда фраза проскочила.

`Alt` отслеживается по обоим фронтам и **не глушится** — в BG3 удержание Alt подсвечивает
добычу, и отбирать это нельзя.

**Чтения «всего вокруг» больше нет ни на одной кнопке.** Тридцать строк про бочки и тростник
не строят картину помещения — это стена, которую приходится выслушивать, и нужное в ней
теряется. Список проходится по одному шагу с фильтром по категории; сводка боя осталась, она
ограничена и отвечает на другой вопрос.

## F16. Три способа, которыми сканер врёт, и что с ними сделано

Устаревшие данные в сканере опаснее их отсутствия: список называет расстояния уверенно, и
проверить его на слух нечем. Найдены три источника, все закрыты:

1. **Игрок ушёл** от точки, где список снят. Порог — три метра (`M.STALE_M2`): меньше значит
   срабатывание на поворот на месте.
2. **Список просто состарился**, пока игрок стоял: мир живёт, существа ходят. Таймер на
   5 секунд (`M.STALE_MS`, `M.scanAt` от `Ext.Utils.MonotonicTime`).
3. **Запись устарела между сканом и фразой** — существо успело сделать шаг, пока игрок
   слушал. Объявляемая запись пересчитывается по живым координатам прямо перед произнесением
   (`refreshEntry`), и это же ловит запись, чья сущность вообще исчезла: предмет подобрали,
   существо умерло, кусок мира выгрузился. Тогда список берётся заново и читается та же
   позиция в нём, а не старое расстояние.

Проверка `Nav.stale()` стоит на шаге по списку, на переключении категории и на «идти к
выбранному». Замер после правки: до скана `stale = true`, после — `false`, `refreshEntry`
возвращает `true`, значения совпадают (персонаж стоял), список 90 объектов в 80 м, 44 из них
в пределах двадцати.

# Сессия 6 — 31.07.2026: создание персонажа как экран, а не как список

## Сводка сессии 6

Экран создания персонажа читался наполовину, и три причины оказались не в нём.

1. **Клавиши слоя вообще не принадлежали экрану.** Создание персонажа — это экран внутри
   запущенной сессии, `nav.me()` отвечает, и `navMode()` на этом основании отдавал все
   команды мировому сканеру. PageDown перечислял бочки, End вёл к задаче, Delete подходил к
   цели, а обозреть экран было нечем. Признак «мир или экран» заменён на фокус (§G1).
2. **Две фразы в одном тике — это одна фраза.** Мост озвучки — файл, переписываемый целиком,
   и второй `say()` затирает первый до того, как спутник его прочитает. Заголовок экрана не
   произносился ни разу за пять сессий; вкладка на `Options_c` — тоже (§G2).
3. **Вкладку читал код, до которого на этом экране не доходило исполнение** — он висел на
   `AlternationIndex` сфокусированной строки, а фокус здесь на крутилке, у которой его нет
   (§G3).

Плюс найдены описания рас и классов, лист персонажа, и виджет подсказки `PinnedTooltips_c`.

## G1. Экран бьёт мир — по фокусу

`navMode()` решал, кому принадлежат клавиши, по наличию персонажа. Верный признак — фокус:
**в сессии не сфокусировано ничего** (§D12, из-за чего чтение в игре и событийное), значит
виджет, который держит фокус Noesis, — это открытая игроком панель.

```lua
if M.screenUp then return nil end        -- клавиши принадлежат экрану
```

`M.screenUp` ставится в проходе читалки и **подтверждается размером**: «что-то заявило фокус»
и «открыт экран» — разные утверждения, и ошибка во вторую сторону отняла бы сканер у человека,
стоящего в поле. Мера та же, что уже отделяет экран от значка HUD в ветке без фокуса
(`#texts >= 8`), и снимается один раз на экран.

Тем же флагом заткнулся мировой HUD: `targetTick`/`cursorTick`/`combatTick`/`questTick` шли
поверх создания персонажа — «Манекен, спутник, 2 из 2, назад, 1 м» между строками листа
персонажа. Теперь они молчат, пока панель открыта.

## G2. Одна фраза на проход

`M.say` пишет `<seq>|<interrupt>|<текст>` в один файл, спутник опрашивает его раз в 10 мс, а
проход читалки идёт раз в ~200 мс. Значит **два `say()` в одном тике — это не две строки**:
второй переписывает файл, и первый не звучит никогда. Так пропадали:

- заголовок экрана (говорился, затем в том же проходе — сфокусированный элемент);
- название вкладки на `Options_c` (`say(tab)`, затем строка списка).

Всё, что хочет сказаться за проход, теперь копится в `M.pending` и склеивается в `flush()` в
одну строку. Порядок — порядок поступления, и он же нужный: где ты, потом на чём ты.

## G3. Экран из вкладок, панели и сводки

Создание персонажа — первый экран, который не список:

```
ls.UIWidget CharacterCreation_c
  Control gamePlayPage
    ContentControl gameplaySubPanel     подробность рядом с колонкой; обычно пуста
    Control gameplayPanel               настройки открытой вкладки и её проза
    Control appearancePanel             та же роль на вкладке «Внешность»
    Grid tabNavigation
      ListBox gameplayTabs              originTab raceTab subRaceTab classTab …
        ListBoxItem raceTab IsSelected=true
    Control summaryPanel                лист персонажа
    ls.LSButton ToggleTooltips          «Подсказки (вкл)»
```

Всё берётся из **ориентиров, которые игра называет сама**, одним обходом, который на каждом
из них останавливается, а не входит внутрь: **~190 узлов вместо 1126**, потому что три панели
и есть почти весь экран. Обход идёт по бамперу, по смене экрана и раз в 2 секунды — не каждый
проход (35–45 мс полный разбор, 9 мс сами ориентиры).

Две ловушки в списке вкладок:

- **Дедупликация только по `Name`.** Визуальное и логическое дерево отдают разные userdata
  для одного элемента, и обход встречает каждую вкладку пять раз: «2 из 13» превращается в
  «15 из 65».
- **Невидимые вкладки не считаются.** `subClassTab`, `spellPrepTab`, `appearanceTab`
  появляются и исчезают по применимости, и счёт разошёлся бы с тем, что обходят бамперы.
  Отсюда «1 из 12» и «9 из 13» в один и тот же вечер — это верно оба раза.

## G4. Проза отличается от подписи длиной, и ничем больше

Описание расы, класса и происхождения — обычный текстовый узел без имени, класса и признака.
Единственный отличитель — длина. Порог 80 **байт** (кириллица по два на букву, то есть ~40
букв): выше самой длинной подписи на экране («Случайно выбранный персонаж», 27 букв) и много
ниже самого короткого описания.

Проза говорится **после значения и только когда сменилась** — она меняется вместе с выбором,
а не с фокусом, поэтому движение по колонке её не повторяет. Длинная намеренно: игрок,
пролистывающий знакомую расу, обрывает её следующим нажатием.

Описание привязано отдельно от значения и может отстать на кадр, поэтому после каждой смены
открывается окно в 4 прохода, и догнавшая проза говорится отдельной фразой с `interrupt=false`
— в очередь, чтобы не разрезать значение пополам.

## G5. Подсказка — это отдельный экран

Внутри `CharacterCreation_c` подсказки нет и не будет. **Back на паде** (`UIPinTooltip` в
таблице привязок; `UIShowInfo` — клик правого стика) поднимает под `ContentRoot` целый виджет
**`PinnedTooltips_c`**, который существует, только пока подсказка закреплена. Слой произносит
его, как только он появился, и берёт первым по клавише подробностей. `WorldTooltips` — другое
и никогда не оно: это подсветка интерактивных объектов вокруг.

## G6. Обзор экрана не обновлялся ни разу

`refreshLines()` был написан, чтобы перечитывать экран на каждое нажатие, и подключён — только
к «в начало». PageUp/PageDown ходили по списку, снятому в момент открытия экрана. На создании
персонажа это худший случай: виджет не меняется никогда, и обзор описывал персонажа, с
которого игрок давно ушёл. Сейчас перечитывание на каждый шаг (68 строк), а списки, которые
построила команда (подробности, сводка), остаются под курсором, пока Home не вернёт экран —
`M.linesFrom`.

## G7. `base` — не всегда крутилка, и почему бюджет обхода несущий

`str(p.Name) == "base"` включало разбор «значение внизу, подпись у предка». Но узлов с таким
именем на экране 73, и читаются они по-разному. Замерено по всем сразу
(`collectText` при 60/8, 200/10, 400/14):

| Узел | 60/8 | 200/10 |
|---|---|---|
| строка сводки | `Сила \| 15` | то же |
| карусель расы | `Раса \| Эльф` | то же |
| навык | `Атлетика \| (×2)` | то же |
| тип тела | `Тип тела \| 1 \| 2 \| 3 \| 4` | то же |
| «Идентифицирует себя как» | `… \| Мужчина` | `… \| Мужчина \| Женщина \| Иное` |
| «Голос» | `Голос` | `Голос` + все восемь голосов |

Отсюда два правила, оба проверены, а не выведены:

1. **Ровно две части, а не «две и больше».** Узел, который читается целиком, отдаётся как
   есть; карусель, оставившая в дереве невыбранные варианты, уходит в разбор с предками,
   который берёт выбранное значение, а не перечисляет возможные. Без этого «Тип тела»
   читался как «Тип тела, 1, 2, 3, 4».
2. **Бюджет 60 узлов / 8 уровней несущий в обе стороны.** Больше — и в чтение лезут
   невыбранные варианты (замерено). Меньше досягаемость — и выбор бонуса на «Способностях»
   читается как «Бонус +1» без характеристики, к которой он применяется: её имя лежит глубже.

Симптом, который это чинило: игрок стоял в листе персонажа на «Интеллект, 10», а слой говорил
**«Сила, Интеллект»** — разбор брал первое слово за значение и одалживал подпись у строки
выше.

## Что изменилось в раскладке

На экране четыре клавиши значат другое, чем в мире, — вопрос тот же, меняется только предмет.

| Клавиша | В мире | На экране |
